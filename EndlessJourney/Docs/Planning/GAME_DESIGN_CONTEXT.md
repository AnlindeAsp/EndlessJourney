## 1. 文档定位

本文件描述 `Endless Journey` 的长期游戏设计方向、核心体验和未来架构约束。

本文件的作用是让开发者、Codex 和后续协作者理解：

- 这个游戏最终想成为怎样的作品；
- 当前原型以外还需要支持哪些长期设计；
- 哪些设计已经确认；
- 哪些只是希望保留的设计意图；
- 哪些内容仍然需要讨论；
- 哪些旧设计已经不再适合作为实现依据。

本文件不是：

- 当前任务清单；
- 当前功能完成状态；
- 当前里程碑；
- 所有旧设计的直接实现要求；
- 所有数值和内容的最终规格。

只有经过确认，并进入以下文档的内容，才能成为正式开发任务：

```text
GAME_DESIGN_CONTEXT.md
→ GAME_PLAN.md
→ FEATURE_TRACKER.md
→ CURRENT_MILESTONE.md
→ GitHub Issues / 实际开发
```

## 3. 状态定义

本文件中的每项长期设计使用以下状态之一。

### Confirmed

已经确认的长期方向。

该状态代表：

- 设计原则已经确定；
- 后续架构不应与其冲突；
- 具体数值和内容仍可调整。

### Design Intent

希望保留的核心设计意图。

该状态代表：

- 概念具有重要价值；
- 具体实现方式仍可优化；
- 不能直接当作已批准的开发规格。

### Unconfirmed

尚未确定。

该状态代表：

- 不得由 Codex 自行选择方案；
- 不得直接加入当前里程碑；
- 需要后续设计确认。

### Deprecated

已经被新方案替代。

该状态代表：

- 旧逻辑不应继续作为实现依据；
- 应在 `DECISION_LOG.md` 中记录替代方案。

# 4. 游戏核心身份

**状态：Confirmed**

`Endless Journey` 是一款以 2D 横版平台探索和动作战斗为基础的游戏。

它的长期核心并不只是：

- 探索地图；
- 获得装备；
- 击败敌人；
- 完成一次冒险。

它还围绕以下主题展开：

- 时间不断向前；
- 人物和故事会结束，但世界继续存在；
- 前代旅行者的行为会影响后来的世界；
- 玩家可以拿走力量，也可以把力量留给后来者；
- 当前时代的最优选择，未必是整个时间线的最优选择；
- 一个完整存档需要体现多个时代之间的继承与后果。

核心主题可以概括为：

> 故事会结束，但旅程不会。  
> 玩家不仅决定自己如何完成旅途，也决定后来者将面对怎样的世界。

# 5. 核心游戏循环

**状态：Confirmed**

长期核心循环为：

```text
探索区域
→ 进行平台挑战和战斗
→ 获得能力、武器、法术和关键物品
→ 解锁新的路线和区域
→ 决定取走、使用、归还、保存或留下物品
→ 完成或未完成当前时代目标
→ 时间推进
→ 下一时代继承前代留下的变化
```

核心循环中最重要的长期差异是：

> 物品和世界资源不只是当前角色的奖励，也是跨时代决策的一部分。

当前原型可以先专注于移动、战斗、装备和敌人，但后续架构不能默认游戏永远只有单一时代和单一角色状态。

# 6. 三时代结构

**状态：Design Intent**

一次完整存档计划包含三个主要时代：

1. 初始时代；
2. 大约一个世纪之后；
3. 再一个世纪之后。

这三个时代不是简单的 New Game Plus。

当前确认方向：

- 每个时代的主角理论上都是一个新的人，只有“灵魂”层面的延续。
- Ability 不作为跨时代永久继承内容讨论。
- 各时代的主角可以重新获得相同或改版后的能力；这些能力通常可以比较简单地重新取得。
- 后续系统设计不应把 Dash、Double Jump、Spell Cast、Dual Wielding 等 Ability 默认写成跨时代继承状态。

未来可能发生：

- 地图结构变化；
- 区域状态变化；
- 地标被修复、损坏或遗忘；
- 前代取走的物品不再出现；
- 前代归还的物品帮助后代；
- 某些物品经过时间成长；
- 某些物品腐坏或失效；
- 某些能力以新的方式重新获得；
- 敌人等级和数量变化；
- Boss出现更强形态；
- 前代未完成的事件继续恶化；
- 新角色通过史书或世界痕迹了解前代行为。

未来架构应预留以下概念的可能性：

```text
SaveProfile
TimelineState
EraState
RegionState
WorldObjectState
PlayerLegacyState
EraOutcome
```

当前阶段不要求立即创建所有类，也不要求提前实现完整三时代系统。

要求只是：

> 当前存档、物品、世界状态和敌人架构不能被设计成只支持一个固定时代的封闭结构。

# 7. 时间与持久化层级

**状态：Design Intent**

未来不同数据可能具有不同的持久化规则。

建议长期区分：

```text
Session State
Working Changes
Last Saved Snapshot
Checkpoint State
Era State
Timeline State
Profile / Meta State
```

可能的含义：

### Last Saved Snapshot / Working Changes

存档点可以理解为一次 `Git merge`。

- `Last Saved Snapshot` 是上一次成功存档后的稳定世界状态。
- 玩家离开存档点后的所有变化都属于 `Working Changes`。
- 如果玩家在下一次存档前死亡，这些 `Working Changes` 会被 discard。
- 玩家回到上一次出发前的状态，而不是保留死亡前取得的临时收益。
- 玩家主动与存档点交互时，当前 `Working Changes` 被合并进 `Last Saved Snapshot`。
- 普通存档会恢复生命和法力，并以恢复后的满状态进入快照。
- 普通存档会清理 ManaOut、负法力、hidden mana debt 等由法力耗尽引发的运行态问题。
- 普通存档会清理中毒、燃烧、减速等短期负面状态。
- 普通存档不会修复护甲，也不会自动恢复诅咒、腐化等特殊长期状态；这些状态按当前值进入快照，除非地点规则另有说明。
- 普通存档点可以打开基础 Storage / Equipment 管理，用于更换武器、法术、护符等基础配置。
- 长期存档架构需要支持“运行态变更”和“已保存快照”的区别。
- 当前原型中部分装备/图鉴数据会即时写 JSON；这与长期存档模型并不完全一致，后续需要重构为可提交/可回滚的保存流程。

### Session State

只在当前运行过程中存在。

例如：

- 当前攻击状态；
- 临时 Buff；
- 当前房间战斗状态；
- 未保存的临时资源。

### Checkpoint State

回到最近存档点后需要恢复或重置的数据。

例如：

- 玩家位置；
- 当前生命；
- 当前法力；
- 当前护甲耐久；
- 当前区域敌人；
- 当前阶段拾取物。

### Era State

在当前时代持续存在的数据。

例如：

- 当前时代已经击败的Boss；
- 当前时代已开启的道路；
- 当前时代NPC状态；
- 当前时代已经取走的关键物品。

当前确认的最小世界状态：

- Boss 是否死亡。
- 门是否打开。
- 区域阻拦状态是否开放。
- 宝箱是否开启。
- NPC 是否移动，需要按内容决定；例如对话后移动位置的 NPC 需要记录。
- 区域状态是否记录，需要按区域内容决定。
- Boss 级别以下的敌人会在存档后重新刷新。
- Boss 击败后不会刷新。
- 击败 Boss 可能导致其区域内普通敌人数量减少，甚至完全消失。

### Timeline State

需要影响后续时代的数据。

例如：

- 物品被取走还是归还；
- 地标是否被修复；
- 当前时代完成度；
- 某个区域是否陷落；
- 某个关键选择是否发生。

### Profile / Meta State

跨越多个存档或完整通关后仍然存在的数据。

例如：

- 特殊成就；
- 解锁模式；
- 通关奖励；
- 特殊初始道具；
- DLC资格。

当前 M3 仍然应先实现简单可靠的普通存档与复活。

M3 不需要直接实现：

- 时间分流；
- Branching Save；
- 三时代迁移；
- 完整 Timeline State。

但普通存档不应被描述为最终唯一持久化模型。

# 8. 时间抗性

**状态：Design Intent**

时间抗性是长期设计中的通用概念，而不应只作为某件物品的硬编码特例。（这个概念还在设计阶段，目前也尚未有涉及其相关的方面）

当前确认方向：

- 时间抗性需要单独专题继续讨论。
- 当前阶段先不把时间抗性纳入具体实现范围。
- 不应在尚未确认的情况下把某类物品默认标记为 Time Resistant。
- 目前明确可能涉及时间抗性的对象主要是背包。
- 背包时间抗性更像游戏剧情过程中的升级，而不是护符临时效果或可自由切换的装备词条。

时间抗性可能应用于：

- 玩家行囊；
- 祝福；
- 地标；
- 世界对象；
- 存档数据；
- 特殊角色状态。

未来可以考虑使用类似的持久性概念：

```text
Temporal Persistence:
- None
- Checkpoint Persistent
- Rollback Resistant
- Era Persistent
- Timeline Persistent
- Profile Persistent
```

以上名称和枚举尚未确认，不应直接实现。

需要保留的设计原则是：

> 不同对象可能对死亡回溯、时间回流和时代推进具有不同抵抗能力。

# 9. 关键物品的世界状态

**状态：Design Intent**

普通游戏中的物品通常只有：

```text
Locked
Unlocked
Owned
```

但本项目未来的重要物品可能需要表达更多状态：

```text
Unknown
Available In World
Taken
Consumed
Returned
Stored
Destroyed
Decayed
Inherited
Time Resistant
Unavailable In Current Era
```

当前关键物品基础状态可以先保持极简：

```text
untaken
taken
```

物品是否能归还不依赖状态枚举，而由物品特性决定，例如 `RETURNABLE`。

物品是否在未来时代保留，也不只由玩家是否拿取决定：

- 有些物品可以被归还；
- 有些物品无法归还；
- 有些物品不拿也会保留到下一个时代；
- 有些物品即使不拿，也不会保留到下一个时代。

归属地点需要记录该物品当前是否仍可被取得。

需要保留的长期设计能力包括：

- 记录物品是否仍在原位置；
- 记录物品被哪一时代取走；
- 记录物品是否已归还；
- 记录物品是否被消耗；
- 记录物品是否存入跨时代容器；
- 记录物品是否因时间成长；
- 记录物品是否因时间腐坏；
- 记录物品是否因时间抗性保留；
- 记录物品是否影响后续地图、敌人或结局。

未来关键物品应拥有稳定、唯一的标识。

不要只通过场景对象是否被销毁来表示长期世界状态。

当前“归还”规则草稿：

- 归还不表示把物品送回所属时代。
- 归还可以表现为交给 NPC、放回某个地点、放入容器、献给某个地标或其他等价行为。
- 不是所有物品都可以归还。
- 玩家通常可能在最终 Boss 战前，或某个 Boss 区域之前，尝试归还可归还物品。
- 归还的主要目的，是把该物品留给未来时代。
- 归还后，当前时代的玩家会永久失去该物品。
- 归还是需要谨慎思考的选择；它通常不会造成非常严重的坏结果，但可能让当前时代后续战斗变得更艰难。
- 可归还物品需要明确标记，而不应默认所有关键物品都可归还。

# 10. 游戏模式与时间规则

**状态：Design Intent**

长期计划中的游戏模式不仅修改数值难度，也会修改时间、死亡和存档规则。

当前阶段：

- 近期开发先专注于标准/经典体验。
- 构想模式已取消。
- 游戏模式当前只保留经典模式和真实模式。
- 真实模式和各种 modifier 先作为长期设计草稿保留，不进入当前实现优先级。
- 难度 modifier 目前主要用于描述硬核/真实模式下可能发生的时代失败惩罚，不应影响 M0–M3 的基础系统实现。

## 构想模式

**状态：Cancelled**

设计意图：

- 更适合体验故事；
- 对过去时间状态有更高自由度；
- 可能允许更自由地返回先前时代或节点。

该模式已取消，不进入当前设计。

## 经典模式

设计意图：

- 时间允许有限回流；
- 回溯可能依赖道具、能力、存档点或其他规则；
- 失败具有代价，但并非完全不可逆。

具体规则尚未确认。

## 真实模式

设计意图：

- 时间单向流动；
- 回溯、复活和拯救类效果受到限制；
- 死亡可能直接推进时代；
- 当前时代完成情况会影响下一时代难度；
- 未完成事件可能导致后续世界恶化。

Codex 应将游戏模式理解为未来的：

```text
Game Rule Set
```

而不是简单的：

```text
Difficulty Multiplier
```

# 11. 死亡模型

**状态：Design Intent**

死亡在本项目中可能有多种含义。

## 普通死亡

- 返回最近存档点；
- 重置当前阶段；
- 恢复部分状态；
- 作为 M3 的第一版实现。

当前确认方向：

- 普通死亡在世界观上更接近“时间回溯”。
- 死亡后玩家应恢复成上一次存档时的 `Last Saved Snapshot`，而不是简单即时治疗。
- 下一次存档前发生的所有 `Working Changes` 都会被 discard。
- 生命、当前法力、隐藏/潜在法力、护甲耐久、位置、背包、钱、消耗品、材料、装备、法术页、铭文、护符、世界对象状态等，都应按存档快照恢复。
- 普通存档点会恢复生命和法力；因此存档快照中的生命和法力通常是满状态。
- 普通存档点会清理 ManaOut、负法力、hidden mana debt，以及中毒、燃烧、减速等短期负面状态。
- 普通存档点不会恢复护甲，也不会清理诅咒、腐化等特殊长期状态，除非未来特殊地点或系统明确允许。
- 门/区域阻拦、宝箱、NPC位置、一次性道具等，如果还没有合并进存档快照，死亡后会回到上一次存档时的状态。
- Boss 级别以下敌人通常会在当前出发期间保持死亡；但玩家下一次主动存档时，世界普通敌人会刷新/重置。
- 普通存档刷新/重置整个世界的普通敌人，但存档点当前 Scene 的敌人不应立刻刷新，以免观感奇怪。
- 只能被杀一次的敌人除外。
- Boss 击败后不会刷新。
- Boss 击杀后会立刻触发一次普通存档行为：生命和法力恢复满，但不保存 Boss 战后的低血低蓝状态；其它状态正常保存。
- Boss 击杀后会在 Boss 房间或附近生成一个预设弱存档点。
- 弱存档点是一次性、无法主动使用的保护点；不允许打开 Storage、菜单功能、装备管理或其它存档点功能。
- 弱存档点可以拥有非常轻微的视觉表现，用于提示 Boss 后保护已生成，但逻辑上不是交互点。
- 如果玩家击败 Boss 后继续探索并死亡，会回到 Boss 房间附近的弱存档点。
- 玩家使用普通存档点后，弱存档点消除。
- 如果背包未来获得时间抗性附魔，则背包相关内容可以例外保留；具体时间抗性规则后续单独设计。

## 死亡回归

- 可能是世界内能力；
- 可能与时间回溯机制相关；
- 不只是菜单中的 Load Game。

## 特殊重组／再凝聚（这个只会在死之间出现，不需要做大考虑）

- 可能不触发普通死亡回归；
- 可能在特殊地点执行；
- 可能用于隐藏能力或计数。

## 真实模式死亡

- 可能直接推动时代；
- 可能保存失败结果；
- 可能提高下一时代难度；
- 可能改变地图和敌人。

## 致命伤害拦截

- 护符或其他效果可能阻止死亡；
- 需要在死亡政策执行前处理。

长期死亡处理建议遵循概念流程：

```text
Fatal Damage
→ Fatal Damage Interception
→ Death Cause
→ Death Policy
→ Respawn / Rollback / Reconstruction / Era Advance
```

具体架构尚未确认。

当前阶段只要求：

- 不要把 `health <= 0` 永久绑定为直接重新加载场景；
- M3 先实现简单可靠的存档点复活。

# 12. 玩家成长类别

## 12.1 Ability

**状态：Confirmed**

Ability 表示通常一旦获得，就不能自由卸下的成长能力。

包括但不限于：

- 冲刺许可；
- 二段跳；
- 滑翔；
- Pogo；
- 攀爬；
- 双持许可；
- 法术使用许可；
- 特殊永久能力。

当前确认方向：

- Ability 不跨时代继承。
- 每个时代的主角是新的个体，可以在本时代重新获得对应能力。
- 重新获得的 Ability 可以是原本版本，也可以是改版版本。
- 因为能力可能会以很简单的方式重新获得，当前不需要把 Ability 继承作为重点系统讨论。

当前原型：

- Ability 由 `PlayerAbilityCore2D` 统一保存运行时解锁状态。
- 当前已接入的能力包括：
  - Dash；
  - Double Jump；
  - Spell Cast；
  - Dual Wielding。
- 能力长期进度从 `PlayerData.json` 的 `unlockedAbilityIds` 读取。
- Dash、Double Jump、Spell Cast 等模块运行时读取 AbilityCore，而不是直接读 JSON。
- 当前已有能力拾取物代码入口：
  - `AbilityPickupItem2D`
  - `AllowDashPickup2D`
  - `AllowDoubleJumpPickup2D`
  - `AllowSpellCastPickup2D`
- 能力获得演出、能力说明UI、永久能力查看页面尚未实现。

## 12.2 Weapon

**状态：Confirmed**

Weapon 是可装备的战斗物品。

基本原则：

- 武器具有独立身份；
- 武器通过数据资产驱动；
- 武器可以切换；
- 武器可能拥有独立铭文；
- 武器类型影响攻击方式和数值；
- 武器修改应由武器系统管理，而不是由UI直接修改玩家基础属性。

当前类型方向包括：

- 单手武器；
- 双持；
- 重武器。

最终武器分类和数量仍可调整。

当前原型：

- 武器静态数据由 `WeaponData` 表达。
- 当前 `WeaponData` 已包含：
  - weapon id；
  - display name；
  - weapon type；
  - length；
  - sharpness；
  - weight；
  - icon；
  - detail image；
  - description；
  - dual wieldable。
- `WeaponLibrary2D` 负责武器资产索引和解锁状态。
- `WeaponEquipped2D` 负责当前装备武器、dual wielding mode 和 record.json 保存。
- `PlayerWeaponSystem` 负责根据当前武器、dual wielding 和铭文计算最终 combat snapshot，并写入 `PlayerCombatCore`。
- 当前玩家不能处于“完全无武器”的装备状态。
- 当前武器公式为原型数值：
  - Sword：`strength * sharpness`；
  - DualBlades：`strength * sharpness * 0.7`，hit count 为 2；
  - Heavy：`(strength + weight) * sharpness`。
- 当前 dual wielding 不直接修改原始 `WeaponData.Type`，而是通过 effective weapon type 让可双持单手剑在运行时视为 `DualBlades`。
- 武器 Storage UI 已支持：
  - 已解锁武器列表；
  - 武器详情；
  - 当前装备高亮；
  - Space 装备；
  - Dual Wielding 按钮。
- 武器获取流程、武技、正式武器平衡仍未完成。

## 12.3 Spell

**状态：Confirmed**

Spell 是可学习并写入法术书槽位的主动能力。

基本原则：

- 玩家可以学习多个法术；
- 只有被写入法术书的法术可以直接使用；
- 法术可能具有吟唱时间；
- 法术可能具有释放时间；
- 法术可能具有冷却；
- 法术消耗法力；
- 法术可能要求地面、空中或方向条件。

当前已确认方向：

- 法术书最终当前规划为 5 页 / 5 个槽位。
- 玩家刚学会法术时，初始只拥有 1 个法术槽。
- 早期表现上，玩家拿到的可以不是完整法术书，而是一张纸。
- 后续会通过进度逐步增加可用法术页。

当前原型：

- 法术静态数据由 `SpellData2D` 表达。
- 当前 `SpellData2D` 已包含：
  - spell id；
  - display name；
  - spell kind；
  - mana cost；
  - cast time；
  - cast lock；
  - cooldown；
  - default cast offset；
  - effects。
- `SpellLibrary2D` 负责法术资产索引和解锁状态。
- `SpellBook2D` 负责法术书页/槽位状态。
- 当前代码支持 1–5 个法术页/槽位；可用槽位数量从 `PlayerData.json -> SpellSlotNum` 读取。
- 当前代码结构与“初始 1 页，后续增加到最多 5 页”的方向兼容。
- 当前页可以为空。
- Storage Spell UI 当前支持：
  - 选择页码；
  - 浏览法术名称列表；
  - 预览法术详情；
  - 写入当前页；
  - 擦除当前页；
  - Space 写入/擦除。
- 同一个法术写入新页时，当前逻辑会从旧页移除，再写入新页。
- `SpellCastSystem` 负责 ability gate、消耗、吟唱、打断、cooldown、cast lock 和 effect 执行。
- `SpellData2D.DefaultCastOffset` 当前已经用于改变 projectile / cast effect 的释放点。
- 伤害法术当前主要通过 projectile 链路实现。
- 治疗法术已有入口。
- Buff 法术当前只有数据入口和 `ISpellBuffReceiver2D` 接口，具体 buff receiver 和规则尚未完成。

## 12.4 Charm

**状态：Design Intent**

Charm 是可装备、可更换的规则修改器。

护符不只提供简单属性加成，还可能：

- 修改冲刺碰撞规则；
- 修改受击击退；
- 增加无敌时间；
- 拦截致命伤害；
- 在触发后破损；
- 根据攻击间隔增加伤害；
- 根据生命或法力状态触发；
- 持续消耗生命换取伤害；
- 复制另一个护符；
- 恢复隐藏法力；
- 修改吟唱、释放和冷却。

未来护符系统可能需要支持：

```text
Stat Modifier
Event Listener
Conditional Effect
Rule Override
Fatal Damage Interception
One-Time Trigger
Breakable State
Effect Mirroring
Equipment Order
```

当前草稿方向：

- 护符存在 `阳刻` 与 `阴刻` 两类占用数值，例如某个护符可以是 `1 阳 / 2 阴`，另一个可以是 `2 阳 / 1 阴`。
- 玩家拥有对应的阳位与阴位容量限制；当前例子可以先按 `5 阳位 / 5 阴位` 理解。
- 护符装备不只是简单固定格子，也不是单一容量点数，而是“阳刻/阴刻双容量”规则。
- 护符只能在存档点或更高级的安全点更换，例如铁匠铺、中心区域等。
- 部分护符可以拥有破损状态、一次性触发状态或需要回到基地/安全点修理。
- 每个护符的阳刻/阴刻消耗值尚未逐个确认。

当前护符图鉴草稿：

| 护符 | 描述方向 | 当前效果草稿 |
| --- | --- | --- |
| 快速吟唱 Quick Cast | 神秘的古代护符，能够精准高效倒流出法力。 | 法术吟唱时间 -30%，释放时间 -30%，冷却时间 -30%。 |
| 法能高效 Mana Efficiency | 安德烈在法力利用效率方面的建树是史上最出色的。 | 法术法力消耗 -30%，理论上额外减少 20% 释放时间。 |
| 大气汲取 Extra Regen | 增加从外界汲取法力的速度。 | 自然法力回复速度 +50%。 |
| 重咒之石 Massive Cast | 很少有人知道这个禁忌，因为知晓它本身就是一个禁忌。 | 所有类型法术伤害 +50%，释放时间 +50%。 |
| 镜像核心 | 倒影并不一定是虚无的。 | 变为上一个护符的镜像；装备顺序会成为规则的一部分。 |
| 水晶凝结 / 水晶核心 / 水晶梦华 | 矿洞之底被水晶拥簇的精华，在岁月的成长中逐渐强大。 | 周目变化：第 1/2/3 周目对应强化版本；受治疗效果 +50% / +75% / +100%，治疗类型法术吟唱时间 -10% / -15% / -20%；可归还。 |
| 无畏之歌 | 先拥有直视的勇气，然后前进的意志。 | 受到敌人攻击或碰撞伤害后不再被击退，并些许增加碰撞后无敌时间。 |
| 守护人偶 | 一刻，只为关键的那一刻。 | 受到致命伤害时免疫本次伤害，之后 9 秒内生命值不会低于 1；护符进入破碎状态，需要到基地修理。 |
| 龙族之力 Dragon's Might | 只有最强大的力量，压倒一切。 | 基础力量 +30%。 |
| 过载 Overload | 超越，超越，无所谓代价。 | 每秒流失 1% 最大生命，造成所有类型伤害 +50%。 |

## 12.5 Inscription

**状态：Confirmed**

Inscription 是附着于具体武器的效果。

基本原则：

- 每把武器独立保存铭文状态；
- 铭文由 Forge 管理；
- 铭文可以修改武器静态属性；
- 铭文可以响应命中事件；
- 部分铭文可能绑定武器；
- 部分铭文可能无法卸下；
- 铭文不应被当作全局玩家Buff。

当前原型：

- 每把武器当前只有一个铭文槽。
- 铭文静态数据由 `WeaponInscriptionData` 表达。
- `WeaponInscriptionLibrary2D` 负责铭文资产索引。
- `WeaponInscriptionEquipped2D` 保存 `weaponId -> inscriptionId` 映射。
- 铭文状态写入 record.json 的 `weaponInscriptionIds`。
- Forge UI 已支持：
  - 选择武器；
  - 选择铭文；
  - Space 篆刻；
  - Backspace/Delete 擦除；
  - R/ESC 关闭。
- 一般铭文允许在铁匠铺操作台自由擦除与印刻。
- 特殊组合例外：
  - `Only.asset` / `Will.asset` 暂时属于拓展武器与拓展铭文，不放入当前游戏流程。
  - `Only` 和 `Will` 存在特殊绑定关系。
  - 该组合无法卸下、无法更改，且该铭文无法被别的武器使用。
- 当前已经生效的铭文效果包括：
  - `WeightMultiplier`；
  - `SharpnessMultiplier`；
  - `ComboDamageRamp`；
  - `MissingHealthDamageBonus`；
  - `ManaOnHit`。
- 静态武器数值类铭文通过 `PlayerWeaponSystem` 影响 effective weight / sharpness。
- 动态命中类铭文通过 `PlayerCombatRuntime2D` 结算。
- 当前原型允许擦除一般铭文；长期需要为 `Only` / `Will` 这类特殊组合预留绑定与不可移除规则。

## 12.6 Armor

**状态：Confirmed**

当前已有的长期方向：

- 伤害减免；
- 耐久；
- 装甲承担伤害；

当前已确认方向：

- 装甲可以存在多种可获得/可切换版本，但数量很少，当前设想约 2–4 种。
- 装甲不使用轻甲/重甲/魔甲等复杂分类。
- 装甲只由两个核心数值定义：
  - damage reduction / 减伤比例；
  - durability / 耐久度。
- 示例装甲方向：
  - 标准护甲：50% 减伤，1000 耐久；
  - 佑护甲：80% 减伤，500 耐久；
  - 韧甲：30% 减伤，1200 耐久。
- 装甲不影响移动、跳跃、冲刺或攻击速度。
- 装甲不跨时代继承；不同时代可以有不同装甲数值。
- 当前优先专注 1 周目，因此跨时代装甲规则暂不展开。
- 装甲没有特殊效果。
- 装甲没有多个部位。
- 装甲修理通过铁匠铺/铁匠对话完成：打开装备、武器、符文等相关界面时默认修复装甲。
- 普通存档点不会修复装甲。
- 装甲装备化时可以采用轻量结构：
  - `ArmorData`
  - `ArmorLibrary`
  - `ArmorEquipped`
  - `Armor UI`
- 装甲切换地点应放在铁匠铺或更高级装备点，而不是普通存档点。

当前实现应视为：

> Armor damage absorption + equipment backend prototype

而不是最终装甲 UI / 完整铁匠铺装备系统。

当前原型：

- `PlayerArmor2D` 是挂在玩家上的单一盔甲耐久模块。
- `ArmorData` 已作为装甲静态资产存在，保存 id、显示信息、最大耐久和减伤比例。
- `ArmorLibrary2D` 已作为装甲图鉴/资产索引存在，支持初始解锁和 record.json 解锁状态读取保存。
- `ArmorEquipped2D` 已保存当前装备装甲 id 到 record.json。
- `PlayerArmorEquipmentSystem2D` 已能把当前装备 `ArmorData` 应用到 `PlayerArmor2D`。
- 当前代码已经具备装甲装备后端，但还没有正式 Forge Armor UI 页面；实际切换仍需要 UI/Inspector 或后续控制器调用。
- `PlayerHealth2D.ReceiveHarm` 可以经过 `PlayerArmor2D` 做 harm damage 减伤。
- `ReceiveDirectHealthLoss` 不走盔甲，也不触发受击无敌。
- 当前盔甲规则：
  - 盔甲有 max durability；
  - 盔甲有 damage reduction；
  - 盔甲承担被减免的伤害；
  - 耐久会按承担伤害下降；
  - 最后一击即使耐久不足也完整提供原有效果；
  - 之后盔甲 broken，不再参与减伤。
- 当前已有 repair / set durability / full restore 代码接口；`OpenForge2D` 已有可选的打开时修理入口，但需要手动绑定 `PlayerArmorEquipmentSystem2D`。
- 当前已有 `ArmorDisplayer`，用于显示盔甲状态。
- 装甲装备化 UI 尚未实现；ArmorData / ArmorLibrary / ArmorEquipped / PlayerArmorEquipmentSystem 后端已实现，仍需 Unity 资产、Inspector 绑定和 Playtest。

# 14. 双持与重武器术语

**状态：Confirmed**

以下术语必须区分：

## Dual Wield

- 同时使用两把单手武器；
- 可能需要双持许可或镜像能力；
- 不等同于双手握持一把武器。

## Two-Handed / Heavy Weapon

- 使用一把重型武器；
- 可能需要双手握持；
- 攻击速度、重量和伤害逻辑不同。

旧大纲中的“双刀”“双手剑”等表述可能存在混用。

未来代码和文档应统一术语，避免将 Dual Wield 和 Heavy Weapon 混为同一类型。

当前原型：

- `WeaponType.DualBlades` 表示双持/双刀类有效攻击类型。
- `WeaponType.Heavy` 表示重武器。
- 单手剑如果 `WeaponData.DualWieldable = true`，且玩家解锁 Dual Wielding，则运行时可通过 effective weapon type 视为 `DualBlades`。
- 该转换由 `PlayerWeaponSystem.ResolveEffectiveWeaponType` 处理，不修改原始 `WeaponData.Type`。
- 本来就是 DualBlades 的武器和单手剑 dual wielding mode 都应进入双 hit / 双动画验证范围。

# 15. 法力模型

**状态：Confirmed**

玩家法力长期设计包含：

- 普通可用法力；
- 隐藏／潜在法力；
- 是否允许透支隐藏法力；
- 隐藏法力下降后的竭尽状态；
- 法力耗尽后的惩罚；
- 法力恢复受到当前剩余法力影响；
- Potential Mana 不满时优先恢复 Potential Mana。

当前实现可以继续优化，但双层法力是长期核心方向。

需要避免：

- 将两层法力永久合并为一个简单的 `0–200` 数值；
- 将所有法力损失都当作普通消耗；
- 忽略隐藏法力透支产生的负面状态。

当前确认方向：

- Forlorn Cast 允许法力进入负数。
- Forlorn Cast 的前提是允许使用 potential mana，即 `PotentialManaAllow` / hidden mana use 必须处于可用状态。
- hidden / potential mana 的恢复优先级高于普通 mana 和其他恢复目标。
- 负法力只应作为运行中的资源债务存在，可以跨场景保留。
- 负法力不应跨存档保留；能到达存档点时，法力会恢复至上限，直接退出游戏或死亡则回到最近存档点状态。
- 恢复药水或主动恢复效果应优先处理 hidden / potential mana，再处理普通 mana。

当前原型：

- `PlayerMana2D` 当前实现了普通 mana 和 potential mana 双层结构。
- `PotentialManaAllow` 控制是否允许消耗进入 potential mana。
- `ManaOut` 表示 potential mana 已耗尽。
- ManaOut 可通过 `PlayerHealth2D.ReceiveDirectHealthLoss` 持续造成生命损失。
- `AllowNaturalRegen` 和 `SetNaturalRegenBlocked` 可以阻止自然回蓝，但不阻止 `RestoreMana` 主动恢复。
- `RestoreMana` 当前优先恢复 potential mana，再恢复普通 mana。
- `SpellCastSystem` 在吟唱阶段会阻止自然回蓝。
- `PlayerMana2D` 代码中已有 `forlornCast` 和 `HasManaDebt` / 负 mana debt 原型入口。
- 后续实现时需要确认当前代码是否完全符合“负法力不跨存档、hidden mana 优先恢复”的最终方向。

# 16. 生命与装甲

## 生命恢复

**状态：Design Intent**

长期方向包括：

- 脱离战斗后缓慢恢复；
- 当前生命越高，恢复越快；
- 生命低于一定阈值时停止自然恢复。

自然回血当前设计方向：

- 自然回血可以像直觉系统一样，随着战斗经历和恢复经历成长。
- 初始例子：每 5 秒恢复 1% 最大生命。
- 玩家通过各种方式累计恢复一定生命量后，自然恢复效率会默默升级。
- 例子：累计恢复 1000 点生命后，自然恢复效率从 1% 提升到 2%。
- 当前草案最多可以提升到每 5 秒恢复 5% 最大生命。
- 具体累计阈值、是否显示升级提示、是否受特殊状态影响，后续实现前再确认。

当前原型：

- `PlayerHealth2D` 已有脱战后自然回血逻辑。
- 当前 harm 入口和 direct health loss 入口已经拆分：
  - `ReceiveHarm(float amount, GameObject source)`：用于敌人/物理世界伤害，会走盔甲、受击无敌和来源记录；
  - `ReceiveDirectHealthLoss(float amount, bool enterCombat = false)`：用于 ManaOut / DoT 等效果类生命损失，不走盔甲，不触发受击无敌。
- 玩家死亡后目前只有死亡状态和事件，尚未实现正式 respawn / rollback / checkpoint 恢复。

## 装甲承担伤害

**状态：Confirmed**

当前方向：

- 装甲具有减伤效益；
- 装甲承担被减免的伤害；
- 装甲耐久随承担伤害下降；
- 装甲破损后无法继续提供完整保护。

当前装备化方向：

- 装甲装备化可以使用轻量 `ArmorData / ArmorLibrary / ArmorEquipped / Armor UI` 结构。
- 装甲切换应发生在铁匠铺或更高级装备点。
- 普通存档点不负责装甲切换或修理。

当前原型：

- 当前盔甲承担的是 harm damage 中被减免的部分。
- 如果盔甲耐久在最后一击不足，也仍然完整提供该次减伤，之后进入 broken 状态。
- Direct health loss 不会被盔甲减免。
- 当前已有 `ArmorData / ArmorLibrary2D / ArmorEquipped2D / PlayerArmorEquipmentSystem2D` 后端。
- `OpenForge2D` 可在手动绑定 armor equipment system 后打开 Forge 时修理护甲。
- 当前没有正式 Armor UI 页面；装甲切换仍需后续 Forge Armor 页面或临时调试入口调用。

# 17. 战斗与统一效果架构

**状态：Confirmed**

未来战斗效果不能只支持简单的定时属性加成。

系统需要逐步支持：

- 固定属性修改；
- 百分比属性修改；
- 条件属性修改；
- 攻击命中事件；
- 受击事件；
- 致命伤害事件；
- 资源变化事件；
- 动作开始和结束事件；
- 持续效果；
- 一次性触发；
- 规则覆盖；
- 可破损效果；
- 效果来源追踪。

可能使用这些能力的系统包括：

- 护符；
- 铭文；
- 法术；
- 武技；
- 永久能力；
- 装甲；
- 敌人特殊能力；
- 环境Modifier。

M1 中的 Buff / Status Effect 架构不应只设计为：

```text
Add 10% Attack for 5 seconds
```

它还必须保留支持事件型和规则覆盖型效果的可能。

当前原型：

- 当前还没有统一 Buff / Status Effect 框架。
- 已存在的效果入口分散在：
  - `PlayerCombatRuntime2D`：处理动态铭文效果；
  - `WeaponInscriptionData`：处理部分静态武器数值修改；
  - `SpellEffectData2D`：处理法术效果；
  - `BuffSpellEffectData2D` + `ISpellBuffReceiver2D`：只作为 buff 法术入口；
  - `PlayerAbilityCore2D`：处理永久能力许可。
- 当前已经实际接入的事件型效果包括：
  - 命中后连击增伤叠层；
  - 根据失去生命计算近战增伤；
  - 有效近战命中后恢复 mana。
- M1 设计 Buff / Status Effect 时，应兼容当前铭文和未来护符/法术/武技，而不是只做一个简单定时属性加成列表。

状态效果当前分类方向：

- 有时间限制的负面效果：例如进入区域获得的虚弱、战斗中被击中造成的流血、短时间力量下降等。
- 这类效果可以通过时间自然结束，例如持续 5 秒的流血。
- 更严重的长期负面状态：例如诅咒。
- 诅咒不会随时间自然消除，通常需要明确的剧情流程、地点、仪式或系统来解除。
- 诅咒不应轻易出现，往往服务于剧情或重要设计。

# 18. 直觉系统

**状态：Design Intent**

直觉系统是一个跨系统的上下文辅助层，不只是教程弹窗。

未来直觉可能读取：

- Boss生命阈值；
- Boss即将发动的大招；
- 精英敌人生命状态；
- 已击败敌人或Boss数量；
- 地图探索进度；
- 已解锁区域数量；
- 玩家当前方向；
- 物品隐藏用途；
- 世界异常；
- 剧情线索；
- 特殊腐蚀状态。

直觉具有以下设计方向：

- 可以在不同界面显示；
- 消息有优先级；
- 消息需要避免重复刷屏；
- 普通直觉可以被特定护符屏蔽；
- 特殊或被腐蚀的直觉不能被屏蔽；
- 直觉能力会随着阅历成长。

当前确认方向：

- 直觉成长由敌人击杀数驱动。

未来各系统应尽量能够发布事件，例如：

```text
BossHealthThresholdReached
BossSpecialAttackTelegraphed
RegionDiscovered
ItemInspected
WorldStateChanged
SpecialConditionDetected
```

当前 M5 只需要实现直觉系统第一版。

# 20. 区域与环境 Modifier

**状态：Design Intent**

区域不只是美术主题，也可以拥有独立规则。

长期可能包括：

- 重力倍率；
- 法力充沛度；
- 法力恢复倍率；
- 生命恢复倍率；

- 下落速度；
- 环境持续伤害；


# 22. 敌人等级模型

**状态：Design Intent**

长期敌人强度分类包括：

- Normal；
- Elite；
- Veteran；（小boss）
- Boss；
- Phantom / Advanced Boss Form。

当前分类说明：

- 普通：最基础类别的敌人，多数没有特殊能力。
- 精英：各项能力更强，可能拥有特殊能力和韧性，可以抵抗部分类型的效果。
- 历战：仅次于 Boss 的超级精锐类型敌人，拥有强大的战斗经验。
- Boss：最强阶级的敌人，需要玩家消耗相当多时间才能击败。
- 虚像：Boss 的更强形态，也代指诸英殿堂中几个残留的形态。
- 普通敌人可以升级为精英，精英可以升级为历战，但历战不会升级为 Boss。

这些等级不应简单等同于完全独立的敌人Prefabs。

长期建议使用组合模型：

```text
Base Enemy
+ Rank Profile
+ Era Modifier
+ World Difficulty Modifier
+ Encounter Modifier
```

可能变化包括：

- 生命倍率；
- 伤害倍率；
- 韧性；
- 特殊能力；
- 行为变化；
- 额外攻击；
- 外观标记；
- 金钱掉落；
- 场景奖励关联；
- 敌人数量；
- Boss阶段；
- Boss虚像形态。

当前掉落规则草稿：

- 怪物理论上除了钱以外，不直接掉落其他东西。
- 一次性道具奖励可以存在，但应主要属于场景逻辑、宝箱逻辑、看守奖励或区域状态，而不是怪物自身通用掉落表。
- Boss 或特殊敌人可以看守关键物品，但关键物品是否获得应由场景/世界对象状态表达。

当前 Rank / 世界难度方向：

- 敌人 Rank 升级属于世界难度设计，当前不需要作为近期敌人行为系统重点处理。
- 世界难度可以直接把一部分怪物替换为其在游戏其他区域出现的上位形态。
- 世界难度也可能叠加统一数值强化。
- 不要求当前阶段确认每个 Rank 是否新增招式或行为。

当前阶段不要求实现完整Rank系统。

但不应默认最终方案是复制：

```text
Enemy
EnemyHard
EnemyHarder
EnemyEra2
EnemyEra3
```

当前原型：

- 当前已有敌人基础模块：
  - `EnemyCore2D`
  - `EnemyHittable`
  - `EnemyHitReaction2D`
  - `EnemyDeathBehaviour2D`
- 当前已有行为模块：
  - `EnemyPatrolWalker2D`
  - `EnemyFloatingWanderer2D`
  - `EnemyStabler2D`
- 当前已有感知与状态机：
  - `EnemyPerception2D`
  - `EnemyBlackboard2D`
  - `EnemyBrainFSM2D`
- 当前已有伤害模块：
  - `EnemyContactAttack2D`
  - `EnemyContactDamageZone2D`
  - `EnemyMeleeAttack2D`
- 当前已有生成器：
  - `EnemySpawner2D`
- 敌人受击 knockback 当前主要受 weapon weight / weapon type 影响。
- `EnemyMeleeAttack2D` 代码存在，但 TestingGround 中 FSM 接线仍需要 M0 Unity 验证。
- Contact damage 理论上一直需要存在。
- Active melee 与 contact damage 可以共存；玩家受伤无敌时间足以避免非预期重复伤害。
- `EnemySpawner2D` 应允许设计者自行选择要生成的 enemy prefab；不强制继续使用旧 `slimeSlider.prefab` 或固定 advanced enemy prefab。
- 当前没有 Rank Profile、Era Modifier、Encounter Modifier 或正式 Boss rank 系统。

# 23. 时代失败与难度继承

**状态：Design Intent**

真实模式下，前一时代的完成结果可能影响下一时代。

当前确认方向：

- 时代完成度目前主要属于真实模式设计。
- 当前暂时根据 Boss 讨伐节奏来判断时代推进与完成情况。
- 标准/经典体验阶段不需要先实现完整时代完成度评分系统。

可能包括：

- 敌人生命提高；
- 普通敌人升级为精英；
- 精英升级为历战；
- Boss出现虚像形态；
- 增加敌人数量；
- 增加危险区域；
- 减少和平区域；
- 未解决事件继续恶化；
- 跳过时代造成更严重后果。

当前难度 Modifier 草稿主要在硬核/真实模式中参考。

难度等级通常为 1-6：

| 等级 | 当前草稿效果 |
| --- | --- |
| 1 | 普通状态。 |
| 2 | 所有敌人血量 +10%，个别敌人变为精英。 |
| 3 | 所有敌人血量 +20%，个别敌人变为精英。 |
| 4 | 所有敌人血量 +30%，部分普通敌人变为精英，个别敌人变为历战。 |
| 5 | 所有敌人血量 +40%，多数普通敌人变为精英，部分敌人变为历战，地图上出现额外普通敌人。 |
| 6 | 所有敌人血量 +50%，部分 Boss 变为虚像，所有精英敌人变为历战，所有普通敌人变为精英，多数地图上额外出现普通敌人与精英敌人。 |

具体公式、敌人升级名单和地图增兵规则仍未确认。

Boss 虚像当前只保留草案：

- 暂不展开具体规则。
- 目前可以理解为 Boss 的各方面强化形态。
- 具体是否增加招式、阶段、奖励/场景状态、外观或特殊机制，后续单独讨论。

当前 M0–M5 不需要实现完整时代难度继承。

# 25. 存档点、Storage 与时间分流

## 当前原型

**状态：Confirmed**

当前存档点相关交互主要承担：

- 打开Storage；
- 更换武器；
- 更换法术；
- 查看或修改装备状态；
- 保存部分当前数据。

当前原型补充：

- `OpenSavingLibrary2D` 通过世界交互打开 Storage。
- `StorageCanvasController2D` 管理 Storage 内部 Weapon / Spell 页面。
- `GameCanvasManager2D` 管理 Gameplay / Pause / Storage / Forge 状态。
- ESC 在 Gameplay 中打开 Pause；在 Storage / Forge / Pause 中关闭当前界面。
- R 在 Storage / Forge 中也可关闭当前界面。
- 当前 Storage 不是完整 Checkpoint / Respawn Point。
- 当前保存范围主要是：
  - 武器解锁；
  - 当前装备武器；
  - dual wielding mode；
  - 法术解锁；
  - 法术书写入槽位；
  - 每把武器铭文；
  - ability unlock；
  - SpellSlotNum；
  - CharmSlotNum 占位。
- 当前尚未保存：
  - 玩家位置；
  - 当前生命；
  - 当前法力；
  - 当前盔甲耐久；
  - 房间状态；
  - 已击败敌人；
  - 已拾取物；
  - 最近存档点复活。

当前设计确认：

- 存档点只有在玩家主动交互时才保存。
- 玩家不交互时，存档点不应自动干涉玩家状态。
- 存档点会把当前 `Working Changes` 合并进 `Last Saved Snapshot`。
- 在下一次存档前死亡，会丢弃这段期间的所有变化，并回到上一次存档快照。
- 普通存档点会恢复生命和法力，并将恢复后的满状态写入快照。
- 普通存档点会清理 ManaOut、负法力、hidden mana debt 等法力耗尽状态。
- 普通存档点会清理中毒、燃烧、减速等短期负面状态。
- 普通存档点不会恢复护甲，也不会清理诅咒、腐化等特殊长期状态。
- 普通存档点允许基础装备管理，例如更换武器、法术和护符。
- 未来存档快照需要支持恢复生命、当前法力、隐藏/潜在法力、护甲耐久、玩家位置、装备、法术页、铭文、护符、背包、钱、消耗品和材料。
- 未来世界状态至少需要记录 Boss 死亡、门/阻拦开放、宝箱开启。
- NPC 是否移动、区域状态是否变化，需要按内容决定。
- 一次性道具如果尚未被保存，死亡后会重新出现在场景中。
- 普通敌人在当前出发期间被击杀后，不会因为离开房间就自动复活。
- 玩家主动存档时，会刷新/重置整个世界的普通敌人，但存档点当前 Scene 的敌人除外。
- 只能被杀一次的敌人除外。
- Boss 击败后不会刷新，并且可能减少所在区域内的普通敌人数量。
- Boss 击杀后会立刻执行一次普通存档行为，并生成一次性弱存档点。
- 弱存档点只提供 Boss 房间附近的复活保护，不允许打开 Storage、装备管理或其它主动功能。
- 弱存档点可以有轻微可见表现，但不作为可交互物体。
- 如果玩家击败 Boss 后继续探索并死亡，会回到弱存档点。
- 弱存档点在玩家使用普通存档点后消除。
- 铁匠铺属于高级存档点，拥有所有普通存档点功能，并额外支持自动修复护甲、更改武器符文等功能。
- 长期上，铁匠铺/高级装备点可以承担更完整的装备管理，例如护甲管理；当前原型已有护甲后端和打开 Forge 时修理入口，但只实现 Forge 铭文相关 UI。
- 铁匠铺不默认清理诅咒、腐化等特殊长期负面状态，除非未来定义其拥有净化功能。
- 消耗品体系本身尚未决定是否进入游戏；战斗中使用道具的体验仍需要之后讨论。
- 如果未来实现消耗品，消耗品存在持有上限，默认按每种消耗品独立计算上限，而不是背包总容量。
- 钱、消耗品和材料默认遵循存档点保存规则；如果背包未来获得时间抗性附魔，则可以成为例外。
- 钱会完全回滚；死亡后敌人也会复活，因此未保存的拾钱结果不会保留。
- 钱默认没有持有上限。
- 已经保存的门/区域道路打开状态会保持打开，即使普通敌人在存档后刷新。

## 长期方向

**状态：Partially Confirmed**

未来以下职责可能需要拆分：

- Checkpoint；
- Respawn Point；
- Storage；
- Equipment Management；
- Fast Travel；
- Healing / Repair。

当前确认方向：

- 不做复杂时间分流或选择管理系统。
- 当前核心只有存档与死亡回滚体系。
- 存档点、Storage、Checkpoint、Respawn 可以按地点等级提供不同功能，而不是进入复杂 Timeline Branching / Timeline Merge。
- 最高级中心点可以提供传送功能；这类中心点每个周目可能只有 2-3 个。

后续需要单独确认：

- 最高级中心点的具体数量和解锁条件。
- 普通存档点、高级存档点、中心点之间的 UI 功能差异。

# 26. 已知设计冲突

## 26.1 法术槽数量

**状态：Confirmed**

旧设计曾出现：

- 同时写入两个法术；
- 同时选择三个法术；
- 法术书升级后增加槽位。

当前设计确认：

- 当前规划为最多 5 页 / 5 个槽位。
- 玩家刚学会法术时只有 1 个槽。
- 初期表现可以是一张纸，而不是完整法术书。
- 后续通过进度逐步增加可用页数。

当前原型：

- `SpellBook2D` 当前最大槽位为 5。
- `PlayerData.json -> SpellSlotNum` 记录当前可用页数。
- 当前 1–5 与已确认的当前规划一致。

## 26.2 二段跳分类

**状态：Confirmed**

解决方案：

- 玩法分类：Ability；
- 世界观分类：Spell-derived Technique；
- 不占用普通法术书槽。

## 26.3 双刀、双持和双手武器

**状态：Confirmed**

解决方案：

- Dual Wield 表示同时使用两把单手武器；
- Heavy / Two-Handed Weapon 表示一把重型双手武器；
- 后续文档和代码不得混用。

## 26.4 当前存档点与最终时间系统

**状态：Partially Confirmed**

当前：

- 主要打开Storage；
- 保存部分装备和能力数据。

未来：

- Checkpoint；
- Respawn；
- Storage；

可能需要拆分。

当前原型：

- 当前存档点交互主要是打开 Storage。
- 当前没有普通 checkpoint / respawn point 的完整实现。
- 当前不做复杂时间分流或选择管理。
- 当前设计确认：存档点只有在玩家主动交互时才保存，不交互则不干涉。
- Storage、Checkpoint、Respawn 会根据地点等级提供不同功能；不进入 Timeline Branching / Timeline Merge 系统。

## 26.5 护符槽位和容量

**状态：Draft Confirmed**

当前草稿确认使用：

- 阳刻/阴刻双容量规则。
- 每个护符拥有阳刻与阴刻占用值，例如 `1 阳 / 2 阴` 或 `2 阳 / 1 阴`。
- 玩家拥有阳位和阴位容量限制；当前例子为 `5 阳位 / 5 阴位`。
- 护符只能在存档点或更高级安全点更换，例如铁匠铺、中心区域等。
- 部分护符可以破损或一次性触发后失效，并需要到基地或安全点修理。
- 每个护符的具体阳刻/阴刻消耗值尚未逐个确认。

当前占位字段不代表最终设计。

## 26.6 装甲装备规则

**状态：Confirmed**

已有装甲减伤、耐久和装备后端原型。

当前设计确认：

- 会存在少量装甲，当前设想约 2–4 种。
- 装甲由减伤比例和耐久度两项核心数值区分。
- 不做复杂类型分类。
- 不影响移动、跳跃、冲刺或攻击速度。
- 不跨时代继承。
- 不拥有特殊效果。
- 不拆分多个部位。
- 通过铁匠铺/铁匠对话打开装备相关界面时自动修理。
- 普通存档点不会修理装甲。

当前原型：

- 玩家身上仍由单一 `PlayerArmor2D` 负责实际耐久和减伤。
- `ArmorData / ArmorLibrary2D / ArmorEquipped2D / PlayerArmorEquipmentSystem2D` 后端已存在。
- 当前支持以 id 保存当前装备装甲，并把 ArmorData 数值应用到 `PlayerArmor2D`。
- `OpenForge2D` 已有可选打开时修理入口，但需要手动绑定 `PlayerArmorEquipmentSystem2D`。
- 当前不支持正式 Armor UI 页面；装甲切换和展示需要后续 Forge Armor 页面。

## 26.7 Forlorn Cast 与负法力

**状态：Confirmed**

当前设计确认：

- Forlorn Cast 允许法力进入负数。
- Forlorn Cast 的前提是允许使用 potential mana。
- hidden / potential mana 的恢复优先级高于其他恢复目标。
- 负法力可以跨场景保留。
- 负法力不跨存档保留；存档点会恢复法力至上限，退出或死亡则回到最近存档点状态。

不得实现负法力长期存档逻辑。

当前原型：

- `PlayerMana2D` 已有 `forlornCast`、`HasManaDebt` 和负 mana debt 相关代码入口。
- 后续需要确认代码与上述规则是否完全一致。

## 26.8 玩家角色基础差异

**状态：Confirmed**

当前确认方向：

- 每个时代只有一个主角。
- 不做同一时代内的多角色模板选择。
- 不同时代主角可以有些许基础数值差异。

未来可能存在的时代差异包括：

- 最大生命差异；
- 法术容量差异；
- 力量差异；
- 法力恢复差异。

这些差异应跟随时代/角色配置，而不是通过性别选择或运行中临时修改 Player Prefab 表达。

2. 不得自行解决 Unconfirmed 项目。

7. 不得将当前原型实现自动视为最终设计。

   - `Needs Design Confirmation`

   - `Needs Unity Verification`
10. 涉及实际体验和平衡时，应标记：

   - `GAME_PLAN.md`

   - `CURRENT_MILESTONE.md`

13. 询问设计问题前，应先根据已确认规则进行基础推断，尤其是 `存档点 = Git merge` 的快照/回滚模型。

# 31. 长期设计摘要

`Endless Journey` 的长期方向可以概括为：

```text
2D平台探索与动作战斗
+
能力、武器、法术、护符和铭文构筑
+
关键物品和世界资源的选择
+
死亡、存档与时间规则
+
三个时代之间的继承和后果
+
玩家为后来者留下的世界
```

当前阶段仍应优先：

```text
稳定项目基线
→ 稳定战斗架构
→ 完成战斗切片
→ 完成普通存档与复活
→ 完成探索区域切片
→ 完成首个Vertical Slice
```

长期设计的作用不是要求当前立即实现全部系统，而是确保：

> 当前短期实现不会破坏未来关于时间、继承、世界状态和跨时代后果的核心玩法。
